# IPPO 算法实现、训练与实验说明

> 适用代码：`algorithms/ippo/` 当前工作区版本
>
> 最后核对：2026-07-31
>
> 本文覆盖：算法思想、Protocol 2.0 接入、状态/动作/奖励前后处理、PPO 训练细节、历史病因与修复、实验配置、指标解释与阶段性结果、文件职责、运行和排障。
> 边界：本文只解释算法侧。SUMO、路网、信号方案和交通需求由仿真侧维护；发现仿真侧问题时只记录和反馈，不在 IPPO 工作中直接修改。

## 1. 当前结论

本项目中的实现不是“20 个完全独立、各有一套网络的 PPO”，而是**参数共享 IPPO（parameter-sharing IPPO）**：20 个路口分别使用本地观测、本地动作和本地奖励，轨迹与 GAE 也按路口独立计算，但所有路口共享同一个 actor-critic 网络。这样既保留了分散执行，也显著提高了样本复用效率。

早期“几乎没有学习、甚至明显差于 fixed”的主要病因不是单一超参数，而是若干训练数据语义错误叠加：奖励被记到了尚未产生效果的当前动作上；不同路口的样本被串成一条时间序列计算 GAE；动作维度补齐后没有 mask 不存在的相位；KL 指标实际上在比较同一个分布；episode 末尾和异常 rollout 的处理也不正确。当前 v4 已修复这些问题，并由 21 个算法测试用例覆盖关键路径。

旧 v3 训练使用不同的状态、网络和 checkpoint 格式，不能作为 v4 的可加载模型。2026-07-31 已清理 v3 权重、checkpoint、训练日志和一次性诊断输出，避免误加载或误当成当前实验结果。

当前只完成了 v4 的真实 SUMO 冒烟验证，还没有跑出同配置、同种子的 v4 与官方 fixed 成对评估。因此现在能确认的是训练链路可运行，**不能严谨宣称 v4 已优于 fixed**。

## 2. 系统边界：谁在控制 SUMO

训练使用的是 Protocol 2.0 的 `local` transport：

```text
train.py
  -> SimulationManager 创建并运行 SUMO episode
  -> SUMO/仿真 worker 独占 TraCI
  -> LocalAlgorithmClient 同进程调用 algorithms.ippo.initialize/step/finish
  -> IPPO 返回 target_phase
  -> 仿真端校验动作并通过安全相位控制器执行黄灯、清空和最小绿灯约束
```

因此：

- IPPO **不直接连接或调用 TraCI**。
- IPPO 通过本地 Python 函数接口接收 SUMO 状态、返回动作；字典结构与 HTTP/JSON 版 Protocol 2.0 相同，只是省去了网络和序列化。
- SUMO 仿真端负责实际灯态、黄灯过渡、冲突清空、最小绿灯、车辆运动和指标汇总。
- 当前 IPPO 只控制信号灯，始终返回 `"vehicles": {}`，不做车速或换道控制。
- `step()` 是同步调用；算法返回前，仿真不会进入下一次决策。

相关接口定义见 [`../../docs/algorithm_interface.md`](../../docs/algorithm_interface.md)，本地传输实现见 [`../../simulation/sumo/local_policy.py`](../../simulation/sumo/local_policy.py)。

## 4. 一轮 episode 的完整数据流

### 4.1 初始化

每轮仿真先调用 `initialize(payload)`：

1. 读取 `IPPO_MODE` 和 `IPPO_MODEL_PATH`。
2. 从 metadata 保存每个路口的 `phase_order`、进口车道和出口车道。
3. 计算统一状态维度和最大动作维度。
4. 训练模式下复用维度兼容的模型、优化器、reward RMS 和跨 episode buffer；拓扑维度变化时重建模型并丢弃不兼容 rollout。
5. 模型模式下从 checkpoint 新建网络并加载权重，同时清除旧优化器引用和 rollout。
6. 清空本 episode 的逐路口轨迹、pending transition 和等待时间基线。

支持的模式：

| `IPPO_MODE` | 行为 |
|---|---|
| `train` | 按分类分布采样动作，记录轨迹，每 4 个 episode 更新一次 |
| `model` | 加载 `IPPO_MODEL_PATH`，对 mask 后概率取 `argmax` |
| `random` | 在该路口合法 `phase_order` 中均匀随机选相位 |
| `fixed` | 永远返回该路口 `phase_order[0]`，仅用于简单算法侧调试 |

> **重要：`IPPO_MODE=fixed` 不是官方 fixed 基线。** 官方固定配时应使用 `SimulationConfig(control_mode="fixed")`，由 SUMO 执行完整的静态信号方案。把第一个相位一直保持不变通常会很差，不能拿来代表 fixed-time control。

### 4.2 每次决策

对路口 `i`，在决策时刻 `t`：

```text
收到当前观测 s_i,t
  -> 计算当前进口道累计等待 W_i,t
  -> 用 W_i,t 完成上一次 pending 动作 a_i,t-1 的奖励
  -> 将 (s_i,t-1, a_i,t-1, r_i,t-1, old_logp, V_i,t-1) 写入路口 i 的轨迹
  -> 从当前 s_i,t 采样或选择新动作 a_i,t
  -> 把新动作保存为 pending
  -> 返回 phase_order[a_i,t] 给仿真端
```

这一步的关键是：**当前观测反映的是上一次动作执行后的结果**。因此当前计算出的等待变化必须归因给 `a_(t-1)`，不能和刚刚从 `s_t` 选出的 `a_t` 组成 transition。

### 4.3 episode 结束

`finish(payload)` 根据结束原因处理 rollout：

- `completed`：正常保留。
- `stopped`：视为时间截断，保留并 bootstrap。
- `error` 或其他基础设施异常：丢弃，不让损坏数据污染 on-policy 更新。
- 正常结束或人工停止时，使用最后观测补完各路口 pending transition；基础设施错误则丢弃整轮 rollout。
- 最后状态的 value 作为 `last_value` 做时间截断 bootstrap。
- 每累计 4 个有效 episode 调用一次 PPO 更新。
- 每 20 个 episode 保存一次模型参数。

## 5. 前处理：从 Protocol 观测到固定维状态

### 5.1 固定维度

每个路口的状态维度为：

```text
8 维当前相位 one-hot
+ 1 维当前阶段持续时间
+ N 维路口身份 one-hot
+ 20 个进口车道槽位 × 5 个特征
= 109 + N 维
```

其中 `N` 是本次训练控制的路口数；20 路口正式训练时状态为 129 维。所有路口共享相同输入形状。进口车道不足 20 时补零，超过 20 时截断；出口车道不进入状态。

### 5.2 特征定义

| 特征 | 处理方式 | 说明 |
|---|---|---|
| 当前相位 | 在 8 维中按 `phase_order` 位置 one-hot | 使用业务 phase ID 到连续索引的映射 |
| `stage_elapsed` | `min(stage_elapsed / 120, 1)` | 120 秒以上截断 |
| 路口身份 | N 维 one-hot | 让共享策略区分路口拓扑与相位语义 |
| `vehicle_count` | `clip(count / lane_capacity, 0, 1)` | `lane_capacity=max(length/7.5,1)` |
| `halting_count` | `clip(count / lane_capacity, 0, 1)` | 与车道长度相关的占用比例 |
| `waiting_time` | `clip(waiting / (200*lane_capacity), 0, 1)` | 按容量缩放的累计等待 |
| `mean_speed` | `clip(mean_speed / speed_limit, 0, 1)` | 使用车道限速 |
| `occupancy` | `min(occupancy / 100, 1)` | 输入按百分数处理 |

如果某个路口观测缺失，状态构建器返回全零向量；正常运行中 Protocol 2.0 应提供所有受控路口。

### 5.3 当前前处理的限制

- 固定上限 `MAX_PHASES=8`、`MAX_LANES=20` 是结构约束；当前实验最大动作数为 4，所以安全，但换地图前应显式检查相位数和车道数。
- 超过 20 个进口车道的路口会截断后部槽位，当前没有警告。
- 路口身份 one-hot 绑定本次训练的路口集合，因此 checkpoint 会校验完整路口身份；不能直接换一组路口推理。
- 归一化常数是人工上限，不是从训练集拟合出的 observation RMS。

## 6. 动作处理与仿真端后处理

### 6.1 离散动作

网络输出统一的 4 维 logits，因为本轮 20 个路口中最大合法相位数为 4。路口 `i` 的动作索引再映射为：

```text
target_phase = phase_order_i[action_index]
```

不同路口相位数不同。`_masked_categorical` 将索引 `>= len(phase_order_i)` 的 logit 设为 `-1e8`，使其概率为 0。训练采样、模型贪心推理和 PPO 重算 log-prob 都使用同一个 mask。

### 6.2 为什么必须保存 mask 信息

PPO 更新需要重新计算旧动作在新策略下的概率。如果 rollout 时用了 mask，而训练时没用相同 mask，概率比 `new_prob / old_prob` 就不再对应同一个动作空间，actor loss、entropy、KL 和 clip fraction 都会失真。因此每个 transition 保存 `valid_action_count`。

### 6.3 SUMO 侧实际执行

IPPO 返回的是目标业务相位，不是直接写入某个 SUMO `tlLogic` phase index。仿真端会先校验 phase ID，再负责：

- 最小绿灯约束；
- 绿灯到黄灯、清空阶段和新绿灯的安全切换；
- 当前尚不能切换时的 pending phase；
- 将最终灯态写入 TraCI。

因此算法连续多次请求不同相位，并不意味着物理灯态会在每 5 秒瞬间硬切。

## 7. 奖励前处理与后处理

### 7.1 原始局部奖励

每个路口只统计自己的**进口车道**等待时间：

```text
W_i,t = sum(waiting_time of incoming lanes controlled by intersection i)
r_raw_i,t-1 = W_i,t-1 - W_i,t
```

- 等待减少：奖励为正。
- 等待不变：奖励为 0。
- 等待增加：奖励为负。

只用进口道是为了让奖励与该路口可控的排队更直接对应，并避免把出口道等待重复计入多个相邻路口。

### 7.2 运行方差归一化

训练使用 Welford 在线算法维护所有路口、所有 episode 的奖励均值和方差。实际送入 GAE 的奖励为：

```text
r_train = clip(r_raw / (running_std + 1e-8), -10, 10)
```

这里**不减 running mean**，是为了保留 `0` 代表“等待没有变化”的语义。日志同时保留原始奖励均值和 RMS 标准差，便于解释交通意义。

### 7.3 回报、优势与批后处理

GAE 必须对每个 episode 中的每个路口分别计算：

```text
delta_t = r_t + gamma * V(s_t+1) - V(s_t)
A_t = delta_t + gamma * lambda * A_t+1
R_t = A_t + V(s_t)
```

当前 `gamma=0.99`、`lambda=0.95`。每条局部轨迹算完后，才把所有路口的样本拼成参数共享训练 batch。拼接后对全 batch 的 advantage 做：

```text
A_norm = (A - mean(A)) / (std(A) + 1e-8)
```

这样既不让 agent A 的下一时刻 value/reward 泄漏到 agent B，又能用所有智能体样本共同更新共享网络。

## 8. 网络与 PPO 细节

### 8.1 网络结构

```text
129-d observation（20 路口配置）
  -> actor body:  Linear(129,128) + Tanh -> Linear(128,128) + Tanh
  -> actor head:  Linear(128,4) -> masked categorical policy

  -> critic body: Linear(129,128) + Tanh -> Linear(128,128) + Tanh
  -> critic head: Linear(128,1) -> local state value
```

当前 20 路口、4 动作模型共有 **66,949 个可训练参数**。actor 与 critic 使用分离的特征网络和正交初始化；critic 只看本路口的局部状态及路口身份，因此仍是 decentralized/local critic，而不是使用全局状态的 MAPPO centralized critic。

### 8.2 参数共享 IPPO 的含义

本实现满足以下分解：

- 每个路口有自己的局部观测 `o_i`。
- 每个路口独立采样自己的动作 `a_i`。
- 每个路口使用自己的局部奖励 `r_i`。
- 每个路口独立形成时间轨迹和 GAE。
- actor/critic 参数 `theta` 在路口之间共享。

参数共享让一次 300 秒 episode 能汇集 20 个路口的经验；路口身份 one-hot 允许共享网络针对不同拓扑学习不同响应。

### 8.3 PPO clipped objective

对 rollout 时保存的旧 log-prob 和当前网络重新计算的新 log-prob：

```text
ratio_t = exp(new_logp_t - old_logp_t)
L_actor = -mean(min(ratio_t * A_t,
                    clip(ratio_t, 1-epsilon, 1+epsilon) * A_t))
```

`epsilon=0.2`。当概率变化超过区间时，clipped surrogate 限制单次更新幅度。

critic 使用 Huber loss，降低偶发大回报误差的影响：

```text
L_total = L_actor + 0.5 * Huber(V, R; delta=10) - 0.01 * entropy
```

反向传播后对全模型做 `max_grad_norm=0.5` 梯度裁剪。

### 8.4 优化器实现

- actor optimizer：actor body + actor head，学习率 `3e-4`。
- critic optimizer：critic body + critic head，学习率 `1e-4`。
- 两套参数互不重叠；总 loss 反向传播后分别更新各自网络。

### 8.5 batch 组织

| 项目 | 当前值 |
|---|---:|
| 累计 episode 数 | 4 |
| 每个正常 episode 的有效样本 | 约 400 |
| 每次 PPO 更新样本 | 约 1,600 |
| minibatch size | 128 |
| 每次更新 epoch 数 | 4 |
| 每个 epoch 的 minibatch 数 | 13（1,600 样本时含最后 64 条余数） |
| 每次 PPO 更新的梯度 step | 约 52 |
| checkpoint 间隔 | 20 episode |

SUMO 每 5 秒提供一次协议决策机会，但 IPPO 默认动作间隔为 15 秒。300 秒时每个路口约 20 条 transition，20 个路口共约 400 条；正常结束时最后观测会补完 pending transition。

### 8.6 诊断指标

| 日志字段 | 含义 | 如何解读 |
|---|---|---|
| `rew_raw` | 原始局部等待差的均值±标准差 | 越大通常表示等待增长越慢，但不能单独替代完整评估 |
| `ret` | 归一化奖励形成的 GAE return | critic 的训练目标，不是秒或车辆数 |
| `val` | rollout 时 critic 预测 | 应逐渐接近 `ret` 的分布 |
| `ev` | `1 - Var(return-value)/Var(return)` | 接近 1 表示 critic 拟合好；不代表 actor 一定优于 fixed |
| `actor` | PPO surrogate loss | 正负本身不等于性能好坏 |
| `critic` | Huber value loss | 持续爆炸或 NaN 才是明显危险信号 |
| `ent` | mask 后动作分布熵 | 过快接近 0 可能策略塌缩；不同合法动作数使最大熵不同 |
| `kl` | sampled-action approximate KL | 监控新旧策略变化；当前未启用 target-KL early stop |
| `clip` | 概率比超出 `[0.8,1.2]` 的样本比例 | 太高表示更新激进，长期几乎为 0 可能过于保守 |

KL 使用与 CleanRL 一致的 sampled-action 近似：

```text
approx_kl = mean((ratio - 1) - logratio)
```

旧实现用当前 logits 构造两个相同分布再求 KL，结果天然接近 0，无法监控真实更新。

## 9. 早期训练效果差的病因与修复

| 病因 | 旧行为/后果 | 当前修复 | 对应测试或证据 |
|---|---|---|---|
| 奖励时序错位 | 用当前 `s_t` 和刚选出的 `a_t` 配当前等待变化；该变化实际由 `a_t-1` 导致 | pending transition 延迟到下一观测再完成 | `test_reward_is_attached_to_previous_action...` |
| 奖励混入出口道 | 汇总观测中的所有 lane，出口排队可能被相邻路口重复计算 | 只汇总 metadata 中的 incoming lanes | 同上，测试用 1000 秒出口等待验证不进入奖励 |
| 多路口 GAE 串线 | 先把所有 agent 样本展平，再逆序算 GAE；agent B 的 reward/value 会回传到 agent A | 每个 episode、每个路口单独算 GAE，再拼 batch | `test_gae_is_computed_separately...` |
| episode 边界错误 | 扁平 buffer 只有最后一个样本 done，其他路口边界无法阻断递推 | 每条局部轨迹独立结束并提供 `last_value` | GAE 两个测试 |
| 时间截断当终止 | 300 秒结束时把后续价值硬设 0，低估未完成车流 | 使用 pending 状态 value bootstrap | `test_gae_bootstraps_a_time_limited_trajectory` |
| 不存在相位可被采样 | 统一 action 维度后，小相位数路口也会从填充动作采样，甚至回退到第一个相位 | rollout、推理和更新全部应用 action mask | action mask 测试 |
| KL 诊断无效 | 新旧分布实际相同，KL 看似完美但没有信息 | 用保存的 old log-prob 和新 log-prob 计算 sampled approx KL | 训练日志中的非零 KL |
| 尾 minibatch 被丢弃 | `floor(total/batch)` 忽略余数样本 | `range(0,total,BATCH_SIZE)` 包含最后余数 | `test_ppo_update...remainder_minibatch` |
| 异常 episode 污染训练 | SUMO/接口错误产生的不完整 rollout 仍可能进入 PPO | 只保留 `completed/stopped`，其他 reason 丢弃 | `test_error_finish_discards...` |
| 模型重载后优化器失配 | optimizer 可能仍绑定旧网络参数 | model mode 清空 optimizer；train mode按当前网络重建 | `test_loading_a_model...` |
| 拓扑改变仍复用旧模型 | 输入/动作维度不兼容，旧 rollout 也可能残留 | 检测输入和 actor 输出维度，重建网络并清 buffer | `test_training_rebuilds...` |
| checkpoint 相互覆盖 | 多次训练共用目录，难以确认模型属于哪次 run | 支持 `IPPO_CHECKPOINT_DIR` 隔离运行目录 | checkpoint directory 测试 |
| 失败后还保存“最终模型” | 中途失败可能被误认为完整 200 episode 结果 | `train.py` 失败即返回 1，且不保存 final model | 训练脚本逻辑 |
| 20 路口长期运行内存压力 | 每轮对象和 SUMO 资源积累，可能触发 malloc/资源问题 | 每轮删除 manager、GC，并尝试清 CUDA cache | 训练脚本逻辑 |

### 12.3 与 fixed 的公平比较

fixed 对照必须使用：

```python
SimulationConfig(
    intersection_ids=["demo_1", ..., "demo_20"],
    period="off_peak",
    duration_seconds=300,
    control_mode="fixed",
    decision_interval=5.0,
    minimum_green=5.0,
    seed=seed,
    step_length=0.05,
)
```

对 IPPO 和 fixed 使用完全相同的种子集合。对每个 seed 计算 paired difference，而不是只比较两个不相关平均数：

```text
Delta_arrived(seed) = arrived_IPPO(seed) - arrived_fixed(seed)
Delta_wait(seed)    = waiting_IPPO(seed) - waiting_fixed(seed)
```

建议报告：

| 指标 | 方向 | 原因 |
|---|---|---|
| arrived vehicles | 越高越好 | 300 秒窗口内完成行程的车辆数 |
| total waiting time | 越低越好 | 与当前奖励目标最直接对应 |
| mean/median waiting per arrived vehicle | 越低越好 | 降低需求规模和完成量影响 |
| time loss | 越低越好 | 比单纯停车等待更完整 |
| queue/halting count | 越低越好 | 反映路口排队 |
| fuel consumed | 越低越好 | 交通效率与能耗 |
| hard braking events | 越低越好 | 安全与平顺性 |

现有 `evaluate_ckpt.py` **只评估 IPPO 模型，不会运行 fixed**，而且汇总字段有限。最终论文/报告用对比应使用一个统一评估 runner 同时跑两种模式、写入同一结果表。训练仍占用大量 CPU 时不要并行启动 5-seed 评估，否则会改变墙钟时间并可能加重 SUMO 资源问题。

### 12.4 300 秒 arrived 的口径限制

当前每轮 departed 约 819，而 arrived 约 75～85。300 秒窗口结束时仍有大量车辆在途，所以 arrived 是一个强截断指标：它既受信号控制影响，也受路程长度和车辆何时进入影响。正式比较必须同时看 total waiting/time loss，并可考虑增加更长评估时长或在需求停止后增加清空期。

## 13. checkpoint 与断点续训限制

当前 v4 checkpoint 保存：

```python
{
    "model_version": "v4",
    "intersection_ids": [...],
    "model_state_dict": ...,
    "reward_rms": {"mean": ..., "var": ..., "count": ...},
    "training_seed_range": [start, end],
}
```

加载时会校验模型版本和完整路口身份，可以阻止旧模型或错误拓扑被静默加载。它仍不是无损训练快照，因为没有保存：

- actor/critic optimizer state；
- 当前 episode 计数；
- 跨 episode rollout buffer；
- NumPy/PyTorch RNG state；
- 训练和仿真配置快照。

因此当前代码**没有真正的断点续训入口**。把某个 `.pt` 作为模型加载后继续 train，即使手工实现，也不会与原运行轨迹等价。正式长期实验应保存一个包含上述状态的字典，并记录代码 commit、配置和命令。

## 15. SUMO 警告与算法影响

### 15.1 路口 891：Missing green phase

日志反复出现：

```text
Warning: Missing green phase in tlLogic '891', program 'demo_19_off_peak' for tl-index 7
```

当前生成的 `demo_19_off_peak` 信号程序有 24 个 link state 字符。检查四个 phase 后，索引 7 在所有 phase 中均为红灯；同时当前 `tls_manifest.json` 中路口 891 的有效 connection link index 列表跳过了 7。也就是说，**当前文件下 index 7 是没有对应受控 movement 的空/未使用槽位**，SUMO 1.12.0 仍对其发出“没有绿灯相位”的一致性警告。

对本轮 IPPO 的判断：

- 该警告在训练和冒烟测试中没有使 episode 失败。
- IPPO 动作是业务 phase ID，不直接操作 link index 7。
- 按当前 manifest，index 7 不承载有效 connection，所以没有车辆因为该槽位永远红灯而被阻塞。
- 因此当前可把它视为**非致命的 SUMO 配置警告，对算法学习没有直接影响**。

但这是基于当前生成文件的结论。如果地图或 connection manifest 以后变化、index 7 出现真实 movement，就必须由 SUMO/路网负责人重新检查。算法侧不修改该信号文件。

### 15.2 Emergency braking

```text
Warning: Vehicle '...' performs emergency braking ...
```

这类警告不会直接让 IPPO 崩溃，也不是 PPO 数值异常。它来自车辆跟驰、冲突、插入或信号变化下的微观交通行为，会间接影响速度、排队和等待，从而进入观测与指标。少量且各 episode 都可正常结束时可继续训练；正式比较应统计 hard braking events，确保 IPPO 和 fixed 使用同一需求与 SUMO 配置。如果数量异常上升，应反馈给仿真侧排查，不在算法目录修改车辆模型。

### 15.3 `Retrying in 1 seconds`

只要后续 episode 正常启动并出现 `EP... OK`，短暂重试通常不是训练失败。若重复很久且没有新的 episode 完成，应同时检查 SUMO 子进程、端口/连接日志、session 状态和系统资源。

## 16. 何时应停止并重修

满足任一项时应停止当前训练并先诊断：

- 出现 NaN/Inf、Python traceback、连续 `FAILED` 或 `TIMEOUT`。
- critic loss 持续多个更新数量级上升，而不是单次波动。
- entropy 很快接近 0 且策略退化为单一相位。
- KL 或 clip fraction 连续显著升高，策略更新失控。
- action validation 报非法 phase、未知路口或协议回显错误。
- reward、arrived、waiting 在多个评估 checkpoint 上持续恶化。
- 发现 topology 超过 8 相位或关键车道被 20 槽位截断。
- fixed paired evaluation 明确显示多个 checkpoint 稳定劣于基线。

仅出现路口 891 警告、零星急刹车、单次 critic 波动，或正常结束时 `partial_completed=20/pending_dropped=0`，不构成停训理由。

## 20. 术语速查

| 术语 | 本项目含义 |
|---|---|
| agent | 一个受控路口 |
| local observation | 该路口相位、阶段时间和最多 20 个相关车道特征 |
| local reward | 该路口进口道总等待的相邻决策差 |
| parameter sharing | 所有路口共用同一 actor-critic 权重 |
| pending transition | 已执行动作但尚未收到下一观测和奖励的临时记录 |
| rollout | 一个 episode 内某一路口的有序 transition 序列 |
| GAE | 用 TD residual 平滑估计 advantage |
| checkpoint | 含 v4 版本、路口身份、网络权重、reward RMS 与训练 seed 范围的 `.pt` 文件 |
| fixed baseline | `control_mode="fixed"` 下 SUMO 官方静态配时，不是 `IPPO_MODE=fixed` |
| local transport | 同进程 Python 调用，协议数据形状与 HTTP transport 相同 |
