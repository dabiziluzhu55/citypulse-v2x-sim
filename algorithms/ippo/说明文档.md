# IPPO v8 算法与实验说明

本文档描述 `citypulse-v2x-sim-ippo-next` 当前可提交版本的 IPPO 实现，包括数据前处理、策略与 PPO、奖励函数、并行训练、后处理与评价、文件职责、实验结果、已知问题，以及与 SUMO 的改动边界。

## 2. 算法边界与数据流

IPPO 不直接创建 TraCI 连接。仿真核心独占 SUMO/TraCI，并通过项目 Protocol 2.0 调用算法模块的 `initialize(payload)`、`step(payload)` 和 `finish(payload)`。

```text
SUMO/TraCI
    │
    │ Protocol 2.0 元数据、路口、车道、车辆实时状态
    ▼
initialize / step / finish
    │
    ├─ 前处理：固定维本地状态 + 候选相位语义 + action mask
    │
    ├─ Actor：为每个候选相位独立打分
    │       └─ 返回 target_phase，请求仍经过既有黄灯/全红安全链
    │
    ├─ 训练：执行对齐 rollout → GAE → 中心 PPO 更新
    │
    └─ 评价：1 s 实时观察 + finish 汇总 + TripInfo 精确回填
```

算法只返回目标相位：

```json
{
  "actions": {
    "signals": {
      "demo_1": {"target_phase": 2}
    },
    "vehicles": {}
  }
}
```

IPPO 不控制车辆速度或换道，也不跳过既有信号灯安全过渡。

## 3. 前处理

### 3.1 初始化元数据索引

`StateBuilder` 在每个 episode 初始化时从 Protocol 2.0 元数据建立只读索引：

- 路口顺序和路口 one-hot 编号；
- 每个路口的可选相位顺序；
- 进口/出口车道顺序；
- 车道长度、限速和估算容量；
- 相位服务的 `(from_lane, to_lane)` connection；
- lane 对应的 edge，以及相位服务的 `(from_edge, to_edge)` movement；
- 相位名义绿灯时长。

车道容量按以下物理近似计算：

```text
capacity_lane = max(lane_length_m / 7.5m, 1)
```

其中 7.5 m 是车辆长度与静止间距的合并近似。所有输入在进入网络前裁剪到固定范围，避免不同路口的车道长度和车流规模造成数量级漂移。

### 3.2 路口本地状态

Actor 和 Critic 的上下文状态由四部分组成：

```text
[当前相位 one-hot]
+ [当前 stage 已持续时间]
+ [路口身份 one-hot]
+ [最多 20 条进口车道 × 5 个特征]
+ [3 个出口拥堵摘要]
```

状态维度为：

```text
obs_dim = 8 + 1 + N_intersections + 5 × 20 + 3
```

20 路口时 `obs_dim=132`。少于 20 条进口车道的位置补 0。

每条进口车道包含：

| 特征 | 归一化 |
|---|---|
| 车辆数 | `vehicle_count / lane_capacity` |
| 停车数 | `halting_count / lane_capacity` |
| 累计等待 | `waiting_time / (200 × lane_capacity)` |
| 平均速度 | `mean_speed / speed_limit` |
| 占有率 | `occupancy / 100` |

出口摘要为出口平均占有率、最大占有率和最大停车/容量比。

### 3.3 候选相位语义

不同路口的“动作 0”通常服务不同 movement。v5a 直接按动作下标输出 logits，容易让共享 Actor 学到无交通意义的下标偏置。v6 起改为 candidate-phase scorer：同一个 MLP 对每个候选相位使用同一套语义特征打分。

v8 每个候选相位有 11 个特征：

| 下标 | 特征 | 含义 |
|---:|---|---|
| 0 | incoming density | 被该相位服务进口车道的平均车辆/容量 |
| 1 | incoming halting | 平均停车车辆/容量 |
| 2 | incoming waiting | 平均等待时间归一化值 |
| 3 | outgoing density | 对应出口的平均车辆/容量 |
| 4 | outgoing occupancy | 对应出口平均占有率 |
| 5 | pressure | `incoming_density - outgoing_density`，裁剪到 `[-1,1]` |
| 6 | current phase | 当前有效绿灯相位为 1，否则为 0 |
| 7 | service age | 距离该相位上次有效服务的时间，除以 120 s |
| 8 | nominal green | 名义绿灯时长，除以 120 s |
| 9 | near demand | `0 < ETA <= 15 s` 的运行车辆需求 |
| 10 | far demand | `15 s < ETA <= 30 s` 的运行车辆需求 |

### 3.4 ETA 双桶来车需求

对速度大于 `0.1 m/s`、下一信号灯为当前路口的车辆，使用：

```text
ETA = distance_to_next_signal / speed
```

随后从车辆当前 `route_index` 向后查找第一个属于该路口的 movement，并只把车辆计入服务这个 movement 的候选相位。已停车车辆由 queue/halting 特征表达，不重复计入来车需求。

两个 ETA 桶分别归一化：

```text
reference = 0.5 veh/s/lane × 15s × served_incoming_lanes
demand = clip(log1p(vehicle_count) / log1p(max(reference, 1)), 0, 1)
```

`--effective-demand off` 只把两个 ETA 特征置 0，网络形状、初始化、奖励和其余输入不变，用于严格配对消融。

### 3.5 动作可用性和防锁相

只有满足以下条件时才产生新的策略动作：

- 当前 stage 是 `GREEN`；
- 没有 `pending_phase`；
- 已满足项目配置的最小绿灯；
- 距离上一次 IPPO 决策至少 15 s。

action mask 同时屏蔽：

- 为异构路口补齐的 padding action；
- 超过最大绿灯时的当前相位。

多相位路口的最大绿灯为：

```text
max_green = max(60s, nominal_green × 2)
```

达到上限后只禁止继续保持当前相位，至少保留一个替代相位。单相位路口不会被屏蔽成无动作。

## 4. IPPO 与网络结构

### 4.1 为什么仍属于 IPPO

每个路口的动作、奖励、轨迹和 GAE 都按本路口独立计算；Critic 不读取全局联合状态，也没有图注意力或中心化价值函数。20 个路口共享参数是为了让异构路口复用训练样本，并通过路口身份 one-hot 区分个体。

因此该实现是“参数共享的独立 PPO”，不是 MAPPO，也不是 CoSLight。

### 4.2 Actor/Critic

Actor 和 Critic 使用完全分离的参数及优化器：

- Actor 上下文编码：`obs_dim → 128 → 128`，激活为 `Tanh`；
- 候选相位评分：`128 + 11 → 128 → 1`；
- Critic：`obs_dim → 128 → 128 → 1`；
- 隐藏层正交初始化；Actor 输出层使用较小增益，避免初始化即形成严重动作偏置。

训练时从 masked categorical 分布采样；正式评估时使用合法动作中概率最大的 deterministic/argmax 动作；random 基线只在相同 action mask 内均匀采样。

### 4.3 执行对齐的 transition

奖励不能直接记到“策略曾经请求过、但信号灯尚未执行”的动作上。本实现把一个 transition 保持为 pending，并在后续实时观测中累计结果；只有到下一次合法决策或 episode 正常结束时才完成 transition。

每条 transition 保存：

- 本地状态、11 维候选相位特征和完整 action mask；
- 采样动作、旧 log-prob、旧 value；
- 实际观测时长；
- delay、停车车辆秒、最大队列、过线量、出口占有率；
- 奖励及各奖励分量；
- `done`、`next_value` 和合法相位数量。

正常时间窗截断时，已获得后续观测的最后动作使用 Critic bootstrap；没有任何后续观测的 pending 动作被丢弃，不伪造奖励。仿真失败或被停止时，整个 rollout 不进入 PPO。

### 4.4 GAE 与 PPO

每个路口轨迹独立反向计算 GAE：

```text
delta_t = r_t + gamma × V(s_{t+1}) × nonterminal - V(s_t)
A_t = delta_t + gamma × lambda × nonterminal × A_{t+1}
R_t = A_t + V(s_t)
```

随后把同一 policy batch 的全部路口样本合并，统一标准化 advantage，并使用 clipped PPO：

```text
L_actor = -mean(min(ratio × A, clip(ratio, 1-eps, 1+eps) × A))
L_actor_total = L_actor - entropy_coef × entropy
L_critic = Huber(V(s), R)
```

当前超参数：

| 参数 | 值 |
|---|---:|
| Actor learning rate | `3e-4` |
| Critic learning rate | `1e-4` |
| `gamma` | `0.99` |
| GAE `lambda` | `0.95` |
| PPO clip | `0.2` |
| entropy coefficient | `0.01` |
| PPO epochs | `4` |
| minibatch size | `128` |
| gradient norm clip | `0.5` |
| Critic Huber delta | `10.0` |

日志同时输出 raw reward、各奖励分量、return/value 尺度、explained variance、Actor/Critic loss、entropy、KL、clip fraction、梯度范数和 ETA 特征分布。

## 5. 奖励函数

v8 保留经过物理尺度归一化的 v5a 局部压力奖励。v6/v7/v8 的主要改动在状态和动作表达，不应误写成 v8 更换了奖励。

### 5.1 总公式

```text
r = clip(-0.60D + 0.20F_safe - 0.15B + 0.05H, -3, 1)
D = 0.45L + 0.40S + 0.15Qmax
```

所有分量在一次实际动作生效窗口内累计，然后按观测时长和物理容量归一化。没有使用随训练历史漂移的 reward RMS。

### 5.2 拥堵成本 D

设本路口进口总容量为 `C`，实际动作窗口时长为 `T`：

```text
L = clip(Σ vehicle ΔtimeLoss / (T × C), 0, 1.5)
S = clip(∫ incoming_halting_count dt / (T × C), 0, 1.5)
Qmax = clip(mean_t(max_lane(halting_count / lane_capacity)), 0, 1.5)
```

- `L` 惩罚车辆相对自由流的时间损失；
- `S` 惩罚持续停车，不会在拥堵稳定时变成 0；
- `Qmax` 关注最拥堵进口车道，避免平均值掩盖局部长队。

### 5.3 安全过线收益 F_safe

车辆的 `next_signal.intersection_id` 在相邻实时观测间发生变化，或车辆从实时集合消失时，算法将其视为越过之前的受控路口。过线量按当时出口回溢风险折减：

```text
F_safe = clip(safe_crossings / (0.5 veh/s/lane × served_lanes × T), 0, 1)
```

它奖励有效吞吐，同时避免把车辆继续送入已接近饱和的出口。

### 5.4 回溢惩罚 B

对出口占有率 `o∈[0,1]`：

```text
h(o) = clip((o - 0.70) / 0.20, 0, 1)^2
B = 0.70 × h(max_average_outgoing_occupancy)
  + 0.30 × blocked_crossings / max(crossings, 1)
```

70% 以下不惩罚，70% 至 90% 二次增长，90% 以上封顶。

### 5.5 等待改善 H

```text
H = clip((waiting_start - waiting_end) / (200 × C), -1, 1)
```

`H` 只占 5%，用于平滑局部等待改善，不再使用容易在稳定高等待状态下失去信号的单一“等待差”奖励。

### 5.6 奖励的已知限制

20 路口训练日志中 `B` 经常接近 0，`H` 也很小，实际梯度主要来自 `D` 和 `F_safe`。这不影响 ep160 已验证的 fixed 对比，但意味着当前奖励仍未充分利用回溢与等待改善项。

曾实验过 v6b 区域队列/切相奖励，结果在 4 个留出 seed 上稳定退化，代码已回退；失败版本不能作为当前算法定义。若继续优化奖励，应做独立消融，不应直接在当前最佳 v8 上同时改变多个分量。

## 6. 同步并行训练

`parallel_train.py` 采用同步 on-policy 结构：

1. 中心 learner 导出一份不可变 policy generation；
2. 每个 worker 使用独立进程、SUMO 会话和 seed 采集一个 episode；
3. worker 不做梯度更新，只返回原始本地轨迹；
4. 中心检查所有 worker 的路口/车道/相位语义元数据；
5. 中心逐参数确认所有 worker 使用同一代策略；
6. 任一 worker 失败时丢弃整个 policy batch；
7. 全部成功后中心执行一次多 epoch PPO，并把新权重发给下一批 worker。

不同交通时段只允许“相位列表末尾缺省”，不允许相位重排、movement 变化或进出口车道漂移。该约束用于防止把不同交通含义的数据误拼成一个 on-policy batch。

最终 v8 训练采用 8 workers。每个 8-episode batch 产生约 3200 条路口决策样本，单批墙钟约 284–291 s。瓶颈主要是多个 SUMO CPU 进程，GPU 对当前小型 MLP 的提速很有限。

## 7. checkpoint 与续训

checkpoint 保存：

- 模型版本、状态维度、动作维度和路口顺序；
- 相位特征 schema、动作周期、最大绿灯系数和 ETA 开关；
- Actor/Critic 权重；
- 两个 optimizer state；
- 已完成 episode 数；
- 训练 seed 范围和训练时段；
- 奖励定义。

续训会在启动 SUMO worker 前拒绝以下不兼容情况：

- v7/v6/旧 raw `state_dict`；
- 路口集合或顺序不同；
- observation/action 维度不同；
- action interval、相位 schema、最大绿灯或 ETA 开关不同；
- 训练时段组合不同；
- checkpoint 缺少 seed 范围。

周期 checkpoint 默认写入最终 `--save` 所在目录下的 `checkpoints/`，避免多个实验进程覆盖全局同名文件。写入采用临时文件后原子替换，失败时删除临时文件。

## 8. 后处理与六项评价指标

### 8.1 数据源

评价不改变六项指标定义，而是按数据能力组合两个来源：

- Protocol 2.0 高频观察：平均排队长度、吞吐量、算法决策延迟、燃油强度；
- 每回合 `tripinfo.xml`：已完成车辆的精确平均行程时间和平均等待时间。

评估器以 1 s 间隔启用 `algorithms.evaluation.observer`。观察器只读取协议帧，不返回控制动作，也不直接访问 TraCI。

### 8.2 指标口径

| 指标 | 计算方式 | 数据源 |
|---|---|---|
| 平均行程时间 | 已完成且未 vaporize 车辆的 `duration` 均值 | TripInfo |
| 平均等待时间 | 同一批已完成车辆的 `waitingTime` 均值 | TripInfo |
| 平均排队长度 | 每个 1 s 帧先对全部受控进口车道 `halting_count` 求均值，再做时间平均 | 实时协议 |
| 吞吐量 | `arrived / simulation_time × 3600` | finish 汇总 |
| 平均决策延迟 | `step()` 内纯算法计算时间的均值，不含 SUMO 推进和进程通信 | `perf_counter` |
| 燃油强度 | 同一燃油车辆集合的累计燃油 L / 累计里程 × 100 km | 实时逐车能耗与里程 |

燃油车辆只包括 `gasoline`、`diesel` 和 `hybrid`。纯电动车、自行车、电动自行车等非燃油车辆既不进入燃油分子，也不进入里程分母。车辆类型缺少 `powertrain` 时不猜测，指标记为 `N/A`。

当前服务器使用 SUMO 1.12。评价模块会自动识别 1.14 前后的燃油单位差异；也可用 `EVALUATION_FUEL_TELEMETRY_UNIT` 显式覆盖。高频帧丢失、已完成车辆数不一致或必要元数据缺失时，相应指标记为 `N/A`，不会用 0 参与平均。

### 8.3 截断车辆诊断

300 s episode 结束时仍有大量车辆未完成行程，因此只看 completed-trip 均值可能产生截尾偏差。`evaluate_paired.py` 还解析 `tripinfo-output.write-unfinished=true` 保存的未完成车辆，并输出：

- completed/unfinished trips 与 completion rate；
- completed trip 的 duration、waiting、timeLoss；
- unfinished waiting/timeLoss 总量；
- 全部已出发车辆的累计 waiting/timeLoss；
- episode 末端 active、remaining、halting、waiting 和 mean speed。

这些是诊断字段，不替换六项正式指标，但用于识别“只让容易车辆完成、把其余车辆留在路网”的伪改善。

## 9. 实验过程与结果

### 9.1 版本演进

| 版本 | 主要变化 | 结论 |
|---|---|---|
| v5a | 物理归一化局部压力奖励、出口摘要、多进程采样 | 20 路口 deterministic 策略出现动作下标偏置和锁相 |
| v6 | 候选相位语义评分、最大绿灯 action mask、执行链诊断 | 修复灾难性锁相，短训已明显超过 fixed |
| v6b | 区域队列与过早切相奖励实验 | 留出评估稳定退化，已回退，不属于当前版本 |
| v7 | 单标量有效来车需求 | 数据链有效，但三组消融增益过小且 timeLoss 略退化 |
| v8 | ETA `0–15 s`/`15–30 s` 双桶需求 | 三组配对消融的 waiting/timeLoss 均同向改善，进入完整训练 |

v8 三组短训消融中，`demand=on` 相对 `off` 的平均结果为：arrived `+4.45%`、全过程 waiting `-4.06%`、timeLoss `-3.89%`。三次独立重复的 waiting 和 timeLoss 均同向，但 pair3 对吞吐改善贡献较大，因此随后只把它作为扩大训练的候选，而没有直接宣称收敛。

### 9.2 完整训练谱系

最终谱系从 v8 pair3 的 ep32 继续：

| 阶段 | episode | 训练 seed | workers | 时段 | 墙钟 |
|---|---:|---|---:|---|---:|
| pair3 短训 | 1–32 | `88301..88332` | 8 | off_peak | 分阶段完成 |
| 完整续训 | 33–160 | `88333..88460` | 8 | off_peak | 4568.8 s |
| 上限检查 | 161–192 | `88461..88492` | 8 | off_peak | 1149.9 s |

每 8 episodes 完成一次同步 PPO 更新并保存 checkpoint。因此 ep161–167 与 ep160 是相同权重，ep169–175 与 ep168 是相同权重；只有 ep160、168、176、184、192 是需要比较的独立策略。

### 9.3 使用项目六项指标选模

统一配置为 20 路口、off_peak、300 s、deterministic 推理和 seeds `62001..62004`。数值为 4 个 seed 的均值：

| 模型 | 行程时间↓ | 等待时间↓ | 队列↓ | 吞吐量↑ | 决策延迟↓ | 燃油强度↓ |
|---|---:|---:|---:|---:|---:|---:|
| **ep160** | 100.53 s | **8.43 s** | 0.08 | 906 veh/h | 12.53 ms | 13.82 L/100km |
| ep168 | **98.91 s** | 9.62 s | 0.08 | 870 veh/h | 12.27 ms | **13.80 L/100km** |
| ep176 | 99.26 s | 9.82 s | 0.08 | 873 veh/h | 12.91 ms | **13.80 L/100km** |
| ep184 | 102.33 s | 9.37 s | 0.08 | **912 veh/h** | 12.40 ms | 13.82 L/100km |
| ep192 | 100.87 s | 8.83 s | 0.08 | 900 veh/h | 8.47 ms* | 13.84 L/100km |
| fixed | 103.04 s | 16.22 s | 0.22 | 744 veh/h | N/A | 14.70 L/100km |

`*` ep192 的延迟在不同服务器负载下测得。所有 checkpoint 的网络结构相同，延迟差异主要反映评测时 CPU 争用，因此不用于策略权重选择。

ep160 的综合排名最均衡，并且全路网累计 waiting 在候选 checkpoint 中最低：

| checkpoint | 全部车辆累计 waiting | 全部车辆累计 timeLoss |
|---|---:|---:|
| **ep160** | **14829.23 s** | 23582.98 s |
| ep168 | 14858.79 s | **23525.76 s** |
| ep176 | 14963.01 s | 23631.12 s |
| ep184 | 14998.16 s | 24021.36 s |
| ep192 | 15111.81 s | 24127.96 s |

ep168 的 timeLoss 只比 ep160 低 57.22 s，但吞吐量低 4.0%；ep184 吞吐量最高，但行程、等待和累计指标弱于 ep160。因此最终选择 ep160，ep184 只保留为“吞吐量最高”的诊断 checkpoint。

相对 fixed，ep160：

- 平均行程时间下降 2.4%；
- 平均等待时间下降 48.0%；
- 平均排队长度下降 63.6%；
- 吞吐量提升 21.8%；
- 燃油强度下降 5.9%。

这证明当前 v8 可以作为远超 fixed 的纯 RL 基线。当前 4 个 off_peak seed 是选模验证集，不是最终测试集；正式提交结果还应使用未参与选模的多时段、扰动场景和更多 seed。MaxPressure 的历史结果尚未全部通过当前六指标管线重跑，不能把旧口径数字混入本表。

## 12. 对 SUMO 的修改边界

### 12.1 实际修改

唯一直接位于 `simulation/sumo/` 下的改动是 session 配置生成器增加：

```xml
<output>
  <tripinfo-output value=".../outputs/sessions/<session-id>/tripinfo.xml"/>
  <tripinfo-output.write-unfinished value="true"/>
</output>
```

这个改动只让每个仿真 session 输出独立 TripInfo，供 episode 结束后的精确评价使用。并行 worker 的 session-id 不同，因此文件不会互相覆盖。

### 12.2 没有修改

本项目没有修改：

- SUMO 二进制或 SUMO 上游源码；
- `.net.xml` 路网拓扑；
- routes、OD 或交通需求生成逻辑；
- `tlLogic` 相位计划；
- 黄灯、全红、最小绿灯等信号安全执行器；
- TraCI 控制权归属。

ETA、队列、奖励和四项实时评价指标全部读取已有 Protocol 2.0 字段。IPPO 仍通过接口请求 `target_phase`，不会绕开仿真侧安全约束。

### 12.3 已知 SUMO 数据警告

```text
Warning: Missing green phase in tlLogic '891', program 'demo_19_off_peak' for tl-index 7
```

该警告表示路口 891 的 `demo_19_off_peak` 程序中，受控 link index 7 没有任何绿灯相位。它属于网络/信号数据问题，不是 IPPO 运行异常。所有对照方法使用同一网络时，配对方向仍可比较，但该 link 的通行能力可能受限，正式赛题数据应由 SUMO/数据负责人确认。

`Retrying in 1 seconds` 通常是本地算法客户端等待新 SUMO/协议服务就绪的启动重试；只要随后 session 正常进入 `COMPLETED` 就不是训练失败。车辆 `emergency braking` 是 SUMO 车流/跟驰警告，会计入 hard-braking 诊断，但不代表 PPO 更新失败。

## 13. 防御性编程与当前精简边界

以下检查必须保留，因为它们防止生成“数值看似正常但实验无效”的结果：

- checkpoint schema、路口、动作周期和实验开关兼容校验；
- 训练与评估 seed 防重叠；
- action mask 至少保留一个合法动作；
- worker 元数据和 policy generation 一致性；
- 任一 worker 失败时整批 on-policy rollout 作废；
- 高频帧或逐车数据不完整时指标记为 N/A；
- checkpoint 临时写入和原子替换。

当前仍有可维护性冗余，但不影响算法定义：`train.py`、`parallel_train.py`、`evaluate_ckpt.py` 和 `evaluate_paired.py` 重复了部分 SUMO 环境初始化、超时清理和 seed 校验；`controller.py` 同时承担状态、奖励、执行诊断和 PPO。准备提交时不应为追求行数减少而临时重构这些已验证路径。后续可在独立提交中抽取公共 runtime/helper，并以完整回归和同 checkpoint 推理一致性作为验收条件。

## 14. GitHub 提交边界

当前本地 `algorithms/ippo/` 约 80 MiB，其中训练过程 `.pt` 模型约 77 MiB、`runs/` 中有 200 余个生成文件。提交内容应包含源码、测试、文档和唯一选中的发布模型：

```text
algorithms/ippo/*.py
algorithms/ippo/说明文档.md
algorithms/ippo/models/ippo_v8_20tls_ep160.pt
algorithms/evaluation/*.py
simulation/sumo/scenario.py

```

若要一并提交跨算法评价接入，再单独检查并暂存：

```text

```

不要提交：

```text
algorithms/ippo/runs/
algorithms/ippo/checkpoints/
__pycache__/
*.pyc
*.log
outputs/
```

不要从 `runs/` 挑选多个相近 episode 一并提交。只有第 9 节按统一六指标选出的 ep160 进入 `models/`；后续若更换最佳模型，应同时更新模型文件、SHA-256 和实验表。

建议把“IPPO 算法与测试”和“六指标/SUMO TripInfo 接入”拆成两个 commit，便于审查和回滚。提交前必须重新运行第 10.6 节命令，并检查 `git status --short`，避免把本地模型和实验日志带入 GitHub。

## 15. 结果解释限制与下一步

- ep160 是当前 4 个固定 off_peak 验证 seed 上的最佳 v8 checkpoint，不等于多场景最终冠军；
- completed-trip 行程/等待必须与吞吐、未完成车辆累计指标一起解释；
- fixed 已用当前六指标管线配对验证；MaxPressure 仍需在同一管线上重跑后才能宣称是否超过；
- 正式结果至少应覆盖 morning/off_peak/evening、扰动场景和更多未参与选模的 seed；
- 若继续优化，优先做奖励分量 `B/H` 的单因素诊断，不要同时改变 Actor、奖励和训练配置。

当前可安全对外表述为：**v8 ep160 是不依赖 MaxPressure 教师的纯 IPPO 基线，在 20 路口统一验证场景中六项交通/能耗指标整体明显优于 fixed；对 MaxPressure 的强基线结论仍等待同口径复评。**
