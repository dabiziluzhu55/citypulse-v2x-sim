# CityPulse Cooperative MAPPO-v1 / v1.1-AS 开发说明

> 2026-08-03 语义更正：早期实现虽使用 centralized critic，但仍以每路口局部奖励和局部回报训练，现统一标记为 `cc_ippo_local_reward`，不再称为 cooperative MAPPO。权威设计见 [`../../docs/superpowers/specs/2026-08-03-cooperative-mappo-v1-design.md`](../../docs/superpowers/specs/2026-08-03-cooperative-mappo-v1-design.md)；历史资产见 [`runs/LEGACY_CC_IPPO_INDEX.md`](runs/LEGACY_CC_IPPO_INDEX.md)。

## 1. 目标与实验边界

Cooperative MAPPO-v1 是一个严格的 CTDE（Centralized Training, Decentralized Execution）基线：

- Actor 在训练和推理时都只读取当前路口的本地观测、候选相位特征和 action mask。
- Critic 训练时可读取按固定路口顺序排列的全局观测。
- 所有受控路口在同一 joint step 共享一个团队奖励：先对各路口 v5a raw reward 取均值，再统一 clip 到 `[-3, 1]`。
- 公平对照 `cooperative_ippo` 使用完全相同的共享团队奖励、joint rollout 和 PPO 配置，只将 Critic 信息范围从 global 改为 local。
- vanilla MAPPO 从随机权重开始。任何 IPPO ep160 权重迁移必须单独命名为 `MAPPO-IPPO-init`，不得计入 vanilla MAPPO 结论。

这个设计的可证伪问题是：在 Actor、共享奖励、状态语义、动作空间、joint rollout、执行链、PPO 超参数和评价口径全部不变时，集中 Critic 的全局信息是否比本地 Critic 产生更有用的团队 advantage，进而改善交通控制。

## 2. 复用 IPPO v8 的 Actor 与工程契约

| 约束 | MAPPO-v1 |
|---|---|
| 本地观测 | IPPO v8 `StateBuilder`，维度 `112 + N` |
| Actor | 共享本地观测编码器 + 候选相位打分器，结构和初始化与 v8 相同 |
| 候选相位 | 11 维特征，最多 4 个动作，相同 action mask 和 `-1e8` 非法 logit |
| ETA | `(0, 15]` 与 `(15, 30]` 双桶 |
| 奖励 | 每路口先计算 v5a raw，再做 `clip(mean(raw_i), -3, 1)` 形成全体 Actor/Critic 共享的 team reward |
| 决策周期 | 15 s |
| PPO | actor LR `3e-4`，critic LR `1e-4`，γ `0.99`，GAE λ `0.95`，clip `0.2`，entropy `0.01`，4 epochs，minibatch 128，grad clip `0.5`，Huber δ `10` |
| 执行语义 | requested phase 实际被观察为 applied GREEN 后，才能形成可训练 transition |
| 并行性 | 多 SUMO worker 只采样，一个中心 learner 统一更新 |

`--model-version cooperative_joint_v1 --reward-scope shared_team --critic-scope global` 是 `cooperative_mappo`；只把 `critic-scope` 改为 `local` 是配对对照 `cooperative_ippo`。两者使用独立随机流初始化 Actor/Critic，所以在 Actor seed 相同时可以保证初始 Actor 逐参数一致。`reward-scope=local` 仅用于历史 `cc_ippo_local_reward` / `ippo_local_reward` 兼容路径。

## 3. centralized-state schema 与 Critic

schema 名为 `centralized_local_obs_pool_v1`。对 `N` 个受控路口，全局状态是：

```text
global_obs: [N, 112 + N] float32
agent_mask: [N] bool
intersection_ids: 与 MAPPOConfig 完全相同的固定顺序
```

建造器要求所有受控路口必须存在，不接受缺失、额外路口、形状错误或 NaN/Inf。mask 是为张量和未来变长扩展预留的；当前真实 worker 不用 mask 掩盖丢失路口。

Global Critic 对每个 synchronized joint step 输出一个 owner-independent 的团队 value：

```text
h_i        = shared_encoder(o_i)
h_global   = masked_mean(h_1, ..., h_N)
V_team     = value_head(h_global)
```

共享编码器保持参数量可控，masked mean 避免总和随路口数缩放。Global Critic 忽略 owner 索引，同一 joint state 不会产生 20 个不同的所属路口 value。Local 对照使用同构的 encoder/head 参数形状，但 context 只来自 owner 的本地观测。暂不引入 attention、GNN、ValueNorm、PopArt、RNN 或奖励归一化。

上述定义对应冻结保留的 `cooperative_joint_v1`。MAPPO-v1.1-AS 使用
`cooperative_joint_owner_conditioned_v1`，只修正 centralized Critic 的 value
语义：

```text
h_global       = masked_mean(shared_encoder(o_1), ..., shared_encoder(o_N))
V_i            = value_head(owner_encoder(o_i), h_global, owner_id_i)
advantage_i    = GAE(reward_team, V_i)
```

同一个 joint state 因 owner 路口不同而产生 20 个 value 和 20 条 GAE 链；训练时
所有 owner 在一次批量 Critic 前向中完成，不重复构造全局状态。Actor 仍只读取本路口
观测、候选相位和 action mask，推理接口完全没有全局输入。旧 v1 checkpoint 继续严格
按单一 team value 语义加载；v1 与 v1.1-AS 的 checkpoint 因 `model_version` 不同而
禁止交叉恢复。

v1.1-AS 没有同时引入 ValueNorm、PopArt、attention、GNN、RNN 或 PPO 调参。这样短训
差异只能归因于 owner-conditioned centralized Critic，而不能归因于 Actor、奖励、
状态、采样量或训练超参数变化。

20 路口路网是异构的：可用相位数为 1–4，入口车道数为 3–19，显式受控路口邻接关系较稀疏。因此 v1 先用全局 pooling 验证 centralized critic 本身的贡献；拓扑/zone critic 是后续 ablation，不与v1同时引入。

## 4. rollout、GAE 和同步更新

每个动作经过 `idle -> awaiting_application -> applied -> transition`。如果 applied phase 与 requested phase 不一致，整个 worker rollout 无效。仿真结束时仅尚未应用的尾部 pending action 被丢弃并记录 `dropped_pending`，已完成的 transitions 仍保留。

Joint rollout 要求每个时间窗口都含有所有配置路口，不允许 partial joint step。每个 worker 只对共享 team reward/value 计算一次 joint GAE，然后把同一 advantage/return 广播给该 joint step 的所有 Actor 样本：

- true terminal：不 bootstrap；
- time-limit truncated：用最后观测的 centralized value bootstrap，但不跨 episode 继续 GAE 递归；
- 不允许同一样本同时标记 terminal 和 truncated。

同步批次在 learner 更新前必须通过：预期 seed 集完整且无重复、所有 worker 成功、无未解决 pending/无效 transition、policy generation 相同、policy SHA-256 相同、状态 schema 与配置签名相同。任一检查失败都不调用 optimizer，也不增加 generation。

## 5. checkpoint 和恢复

checkpoint 用临时文件 + `fsync` + `os.replace` 原子保存，内容包括：

- Actor、Critic 及两个 optimizer；
- episode 和 policy generation；
- 路口顺序、本地/全局状态 schema、相位特征 schema；
- PPO、奖励、决策周期、ETA 开关等关键配置；
- Actor/Critic 初始化 seed、已用训练 seed 范围和 period；
- Python、NumPy、Torch CPU/CUDA RNG 状态；
- `algorithm_variant`、`reward_scope`、`team_reward_schema`、reward 聚合/裁剪阶段、`critic_target_scope` 和 `joint_step_schema`；
- 可选迁移源 SHA-256。

`--checkpoint-every` 默认为 20 episodes。周期 checkpoint 只在一个完整批次完成更新后保存到 `checkpoints/<name>_epXXXXXX.pt`，不会保存失败或部分批次。恢复前会先验证 metadata，不兼容时不会先污染内存中的模型和 optimizer。

## 6. 评价口径和 MAPPO 是否“超越” IPPO

使用现有六项正式指标，不改计算源：平均行程时间、平均等待时间、平均排队长度、吞吐量、平均决策延迟和油耗强度。丢帧、TripInfo 不完整、燃料单位/车型不可验证等情况必须记为 `N/A`，不得补 0。

不以单一 seed、单一最佳 checkpoint 或训练 reward 宣称超越。配对实验需要：

1. `cooperative_ippo` 与 `cooperative_mappo` 使用相同共享奖励、Actor 初始权重、训练 seed、period、episode 数和仿真时长，只改 Critic 的 local/global context。
2. 评估使用完全相同且未参与任一训练的 seed。配对汇总会强制检查 seed 隔离。
3. 对每个 seed 先计算 `MAPPO - IPPO` 差值，再汇总均值、中位数、标准差和 bootstrap 95% CI；缺失配对保留 `N/A`。
4. 同时查看 critic 的 pre/post/next-rollout explained variance、per-agent EV、return/value 标准差、advantage 幅度、KL、clip fraction 和梯度范数。总体 post-EV 不能单独证明 Actor 获得了更好的 advantage。
5. 记录唯一 joint state 数、`(joint state, mask, owner)` 有效 Critic 输入数、rollout value 重放误差、动作占比和未选中有效动作比例；后者只是短窗口代理指标，不等同于完整 phase-starvation 结论。

Cooperative MAPPO 有机会超越同奖励的 cooperative IPPO，因为全局 Critic 可以用跨路口状态解释团队回报；但不保证。稀疏拓扑、全局 pooling 的无关噪声和有限样本都可能让它与本地 Critic 持平或更差。与原 IPPO v8 的结果可作工程参照，但因 reward scope 不同，不能单独归因于 centralized critic。

## 7. 文件导航

| 文件 | 责任 |
|---|---|
| `features.py` | IPPO v8 本地特征适配与 centralized-state builder |
| `models.py` | 本地 Candidate Actor、local/global Critic 和 RNG 隔离初始化 |
| `reward.py` | 无全局副作用的 v5a reward accumulator |
| `rollout.py` | requested/applied 对齐状态机、transition 和 terminal-aware GAE |
| `controller.py` | Protocol 2.0 采样器，本地 Actor 决策和 centralized value |
| `parallel_train.py` | worker 批次验证、GAE 组批和 generation coordinator |
| `trainer.py` | 中心 PPO learner 与训练诊断 |
| `checkpoint.py` | 原子 checkpoint、兼容性验证和完整恢复 |
| `train.py` | 同步多 SUMO worker/单 learner 训练入口 |
| `evaluate_paired.py` | seed 隔离的配对差值汇总 |

## 8. 分阶段验证

```bash
# 静态回归 + MAPPO 单元测试
python3 -m pytest -q algorithms/ippo algorithms/evaluation algorithms/mappo
python3 -m compileall -q algorithms/mappo

# 4 路口短 smoke（随机初始，非全量训练）
python3 -m algorithms.mappo.train \
  --model-version cooperative_joint_v1 --reward-scope shared_team \
  --critic-scope global --init random --intersections 4 \
  --episodes 4 --workers 4 --duration 120 --base-seed 93001 \
  --period off_peak --actor-init-seed 42 --critic-init-seed 43 \
  --checkpoint-every 4 \
  --save algorithms/mappo/runs/cooperative_smoke_4tls/cooperative_mappo.pt
```

论文语义对齐后的 v1.1-AS 仅替换 model version，并使用独立输出目录：

```bash
python3 -m algorithms.mappo.train \
  --model-version cooperative_joint_owner_conditioned_v1 \
  --reward-scope shared_team --critic-scope global --init random \
  --intersections 4 --episodes 1 --workers 1 --duration 120 \
  --base-seed 95701 --actor-init-seed 42 --critic-init-seed 43 \
  --checkpoint-every 1 \
  --save algorithms/mappo/runs/cooperative_mappo_v1_1_as/smoke_4tls_seed95701/cooperative_mappo_v1_1_as_ep1.pt
```

20 路口门槛实验固定为 8 worker、300 s、ep32，并用三个互不重叠的训练
seed 组做旧 v1 / v1.1-AS 配对。每组另用 8 个未参与训练的 seed 做确定性评估。
短训只用于判定训练链健康与是否存在可重复的吞吐/等待优势，不据此启动 ep160。

smoke 通过后必须先汇报，再决定是否进入 20 路口 local/global Critic 的同 seed 短训。在短训证明 generation、checkpoint 恢复、PPO 诊断和交通指标链都健康之前，不启动长训。

## 9. 已知的上游 SUMO 现象

`demo_19` / TLS 891 存在“缺少 green link index 7”的已知警告。MAPPO 开发不修改路网、routes、tlLogic、交通需求或上游控制代码；该问题只记录和上报。

## 10. v1.1-AS 短训结论

三组 20 路口、8-worker、ep32 配对短训和共 24 个 held-out 评估 seed 已完成。
v1.1-AS 相对旧 v1 的平均旅行时间和已完成车辆平均等待显著改善，但吞吐无显著优势；
平均队列、油耗、未完成车辆 waiting 和 all-traffic waiting 显著恶化。第 3 组还出现
一条 junction collision 警告。

因此按预注册 hard stop，v1.1-AS 不晋级、不跑 ep160，作为 Cooperative MAPPO 基线
与负结果保留。完整数字、置信区间、checkpoint 和已知风险见
[`runs/cooperative_mappo_v1_1_as/PAIRED_SHORT_REPORT.md`](runs/cooperative_mappo_v1_1_as/PAIRED_SHORT_REPORT.md)。
