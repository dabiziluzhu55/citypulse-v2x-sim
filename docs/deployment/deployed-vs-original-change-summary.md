整理日期：2026-09-12
版本范围：从 develop 部署准备到 fix3，依据已经保存的代码差异、构建和验收记录整理。补充复查了当前服务健康、配置路径及前端评价逻辑；历史性能和 AI 数据没有重新测量。详细操作见 [部署与运行说明](deployment-runbook.md)。

## 1. 总体结论与比较范围

部署版的主要变化是：将已有系统整理为独立容器部署，隔离 Backend 与 SUMO，完善地图资源和密钥配置，修复车辆坐标、3D 切换回滚及统计数据链路，并对交通流生成器的候选处理阶段实施等价优化。

**已取得的主要效果：**

- 三个对照场景结束时，部署版与原版的车辆集合及完整车辆数据一致。
- 同一份完整快照输入原版和修复版统计类，三个场景的全部指标输出一致；没有修改统计公式来人为贴近某一组数值。
- 交通流候选处理阶段单次对照从 153.62 秒降至 35.60 秒，耗时减少约 76.8%，候选结果完全一致。
- 真实 AI 接管、恢复和结束流程通过短时验证；部署版可以独立运行。
- 3D 瓦片加载延迟、百度在线瓦片授权问题及约定暂缓的道路/建筑问题仍有保留项。

## 2. 部署结构与环境改动

| 改动 | 原因/原状态 | 实现方式 | 效果与边界 |
|---|---|---|---|
| 独立容器部署 | 原开发版使用本机开发目录、Conda 和本地仿真管理器；部署应能独立维护 | Compose 管理 Frontend、Backend、SUMO Worker、Redis，发布目录、私有配置、持久数据分开 | 更新部署版不会覆盖原开发副本；支持保留旧镜像回滚。原项目已存在 Redis/Celery 路径，本次不是从零重写分布式架构 |
| Backend/SUMO 隔离 | Redis 模式仍有经评估、场景导出、AI runtime 间接加载 SUMO 的路径 | 将路径定义、车型解析、作用域和场景 XML 编译迁入 simulation_protocol；旧导入路径保留兼容别名；本机 runner 延迟导入 | Backend 无需安装或加载 SUMO 内核，仍支持地图、导出、预测和 AI 服务；SUMO 在 Worker 执行 |
| API 依赖检查修正 | Redis 模式地图请求仍可能因没有 SUMO_HOME 返回 503 | 仅 local 模式检查 SUMO_HOME，Redis 模式检查管理器和生成产物是否就绪 | 后端隔离后地图和导出接口仍能工作；服务不可用时明确报错 |
| 依赖与模型对齐 | 同名 SUMO 版本不一定是相同二进制；模型或运行设备变化可能影响效果 | Worker 使用与原环境一致的 Ubuntu SUMO 1.12 包；预测/嵌入模型沿用原模型，使用 CPU；Qwen 继续调用已有服务 | SUMO 二进制及相关模型曾进行一致性检查；不向原 v2x-ai-py310 安装或升级依赖。Qwen 是外部依赖，不由这套 Compose 管理 |
| 私有 SSH 验收入口 | 当前选择先通过 SSH 隧道访问 | 前端绑定服务器回环地址 18080，应用内部通过 Docker 网络通信；允许部署网络访问已有 Qwen 服务 | 未新增公开 Web 入口；同伴需建立各自隧道。没有额外实现公网登录系统 |
| 静态视频发布 | 路侧视频需要稳定读取与拖动播放 | 视频作为独立挂载资源，Nginx 支持 Range 请求 | 三个已测路侧视频返回 HTTP 206；大视频不随应用镜像重复打包 |

## 4. 运行正确性修复

### 4.1 会话启动

**原因：** 原代码调用未定义的 `_read_json`，导致会话初始化失败。
**方式：** 使用 UTF-8 读取文件，并通过 json.loads 解析清单。
**效果：** 独立对照副本和部署版可正常启动仿真；没有因此放宽清单校验或改变交通需求。

### 4.2 3D 切换失败回滚

**原因：** 原有切换先移动镜头，再确认车辆/场景准备情况；部分失败路径只放弃新场景或恢复路口选择，没有一起恢复镜头。这个缺口在原版也存在。

**方式：** 保存已提交镜头检查点；当前切换失败时统一取消车辆过渡、恢复路口选择和镜头；旧事务不能回滚新事务；输出具体失败原因。

**效果：** 单元测试覆盖镜头状态恢复及取消旧事务。浏览器注入路口 19 环境清单 HTTP 500 后，选择由路口 2 切向 19，再恢复为 2；运行中切换路口 3、14时，最终选择与场景标记对应。

**边界：** 浏览器注入验证覆盖资源加载失败，镜头检查点由单元测试验证；不是所有失败类型都逐项做了浏览器注入。瓦片下载、解码和绘制的延迟没有因此全部消失。

关键文件：[3D 组件](../../frontend/src/components/visualization/BaiduThreeMap.vue)、[镜头检查点](../../frontend/src/utils/mapViewCheckpoint.ts)、[地图视图管理](../../frontend/src/composables/useAppMapView.ts)。

### 4.3 快照顺序与终态

**原因：** Redis 订阅可能先读取最新快照，再收到队列中的旧消息，已复现 `1 → 3 → 2 → 3`。另外，原协议的最终状态可能复用上一帧序号，单纯按序号去重会漏掉终态。

**方式：** 订阅层拒绝旧序号、重复数据，兼容同序号的合法终态转换；Worker 的新终态使用递增序号。

**效果：** 倒序和终态回归通过；新会话能够正常进入 COMPLETED 并完成指标结算。终态兼容是本轮测试发现后补齐的内容，最终发布包含该修正。

关键文件：[Redis client](../../simulation_protocol/client.py)、[Worker 发布](../../simulation/sumo/engine/distributed/tasks.py)。

### 4.4 指标去重与可靠采样

**原因：** 区域指标跟踪器收到旧帧后可能降低“上次累计值”，再次收到新帧就重复累计；原版本地订阅队列容量为 1，还可能覆盖中间帧。最终车辆位置相同不能保证过程统计相同。

**方式：**

- 在更新区域成员和累计数据之前拒绝倒序、重复时刻，并保留诊断提示。
- Worker 将每个发布快照压缩写入独立会话的 evaluation.sqlite，指标订阅按序补读；页面仍使用实时推送。
- 数据记录与 Redis 发送复用一次 JSON 序列化，SQLite 连接明确关闭。

**效果：** 三个场景的在线等待时间、平均排队长度、吞吐量、制动次数与独立重放一致；原/新统计类使用同一完整输入时全部指标载荷相等。

**代价与边界：** 增加磁盘写入和保留空间。本轮每个 300 秒会话约增加 21–33 MiB；保存的是 1 秒间隔的发布快照，不是每个 SUMO 内部步。已有读取链路支持重放，不意味着所有崩溃恢复场景都已做故障注入。

关键文件：[指标采集](../../traffic_eval/collector.py)、[快照记录](../../simulation_protocol/snapshot_journal.py)、[指标订阅循环](../../backend/app/services/simulation_service.py)。

### 4.5 WebSocket 与容器地址更新

| 问题 | 修改方式 | 效果 |
|---|---|---|
| WebSocket 首次同步读取可能阻塞异步事件循环 | 首次读取也通过 asyncio.to_thread 执行 | 消除这一处同步等待；没有单独宣称接口吞吐量提升比例 |
| 后端容器 IP 改变后，Nginx 缓存旧地址可能返回 502 | 配置 Docker DNS 动态解析 backend | Nginx 配置检查通过，更新后健康接口恢复；避免固定使用容器启动时解析的旧地址 |

关键文件：[WebSocket 接口](../../backend/app/api/v1/simulations.py)、[Nginx](../../frontend/nginx.conf)。

## 5. AI 与算法一致性

本轮没有重训模型、替换算法，或为了展示效果修改需求强度与评价公式。部署版尽量沿用原版模型与运行参数。

| 调整/验证 | 原因与方式 | 结果 |
|---|---|---|
| AI 参数对齐 | 将部署配置补齐为原版 AI 超时 90 秒、Copilot 超时 60 秒，二者最大输出 512 tokens | 避免缺省值不同导致行为差异；参数写在私有配置中 |
| 预测与嵌入 | 沿用 NarrowNet-TDP 和原嵌入模型，CPU 执行；Qwen 使用现有服务 | 已有部署验收记录包含预测非回退、RAG 实际检索和问答；不是本轮重新验证所有模型精度 |
| 六算法流程 | fixed、max_pressure、sotl、ippo、mappo、cov2x 运行与并发任务验证 | 已测任务均完成；这不是六种算法控制效果的排名或精度证明 |
| fix3 真实 AI 闭环 | 90 秒仿真，路口 14 配置限速扰动，Max Pressure 为基线 | 墙钟约 100.36 秒，INACTIVE → ACTIVE → RECOVERY → FINISHED，计划序号达到 5，最终 COMPLETED，未记录 AI 错误 |

AI ObservationV2 控制路径本身不要求 RAG。应区分“AI 接管闭环通过”和“Copilot 的 RAG 检索通过”，不能混写成同一个验证结果。

## 6. 交通流生成器专项优化

### 优化原因与方式

真实 20 路口数据的 cProfile 分析显示，候选路线匹配和筛选占据大量 Python 处理时间。原 `_route_contains` 在路线每个位置反复建立切片、比较目标路径。

新实现使用序列原生索引先定位目标首边，再只在候选位置比较完整路径，减少无关位置的扫描开销；保留空路径、重复边、缺失边和 tuple/list 输入语义。

没有改变随机种子、车型、需求量、候选选择标准或质量门槛，也没有通过关闭验证获取提速。

### 实测效果

比较使用同一批四类车辆的 duarouter 输出，计时覆盖候选读取、匹配和筛选，排除重新路由带来的差异。

| 指标 | 原版实现 | 优化后 |
|---|---:|---:|
| 候选处理耗时 | 153.62 秒 | 35.60 秒 |
| 相对加速 | 1 倍 | 约 4.32 倍 |
| 耗时减少 | — | 约 76.8% |
| 完整候选结果 | 基准 | 与基准完全一致 |

两份结果 SHA-256 相同：`cc68594ab0199b67f2e546b9ceb12fb89b753c7ef5e17dea3ff2c130aaaba6c2`。另有 5000 组随机输入的等价测试通过。

**这是单次、候选处理阶段的对照结果。不能写成“整个系统提速 77%”“SUMO 仿真提速 4 倍”或“GPU 性能提升”。** 带 cProfile 的耗时只用于定位，不直接参与上述提速比例计算。

代码：[匹配实现](../../simulation/sumo/building/build_traffic.py)、[可复用对照脚本](../../scripts/deployment/benchmark_traffic_candidates.py)、[等价测试](../../tests/deployment/test_traffic_matching.py)。

### 8.1 本次新增复查：量化评价显示与解释

**问题位置：** `frontend/src/utils/evaluationComparisonMetrics.ts` 的 `hasFinishedFixedBaseline` / `buildAdvantageMetrics`，以及 `frontend/src/components/dashboard/RightSidebarPanel.vue` 的 `displayedAdvantageMetrics`。

四项“交通效能提升”是相对固定配时的百分比。当前组没有 `algorithm=fixed` 且 `finished=true` 的记录时，全部为空；基线为零或指标缺失也不能计算百分比。这一门槛具有对照意义，但只显示横线会误导用户。建议增加明确的缺基线提示，不应使用虚构基线填充数据。

比较组按场景、控制范围、时段、时间窗口、车流来源、扰动、随机种子和步长区分；算法、播放速度和观看路口不影响分组。本地记录依赖浏览器 localStorage，最多 8 组、每轮 200 点，不自动跨浏览器和访问端口共享。服务器保留会话数据并不代表浏览器自动恢复所有比较索引。

**另外发现的实际展示偏差：** CoV2X 运行过程中会缓存最近有意义的正向提升，后续值变差时可能继续显示此前正值；最终评价才使用原始终态值。通过 `git show 6f18a23` 对照，确认该策略在原基线中已有，不是 fix3 新增。建议后续取消正值保留，展示真实有符号过程值，并区分过程/最终状态。本次仅记录问题，没有修改业务代码，也没有将其算作已完成修复。

**本轮验证：** 评估对照、提升和报告三个现有测试文件共 48 项通过，包含基线缺失、同进度比较、零分母和终态报告条件；测试也包含原正值保留策略，测试通过不代表该产品策略合理。

**服务器只读状态：** 三个应用镜像标签均为 fix3；四容器运行，Backend/Redis 健康，Worker ping 返回 pong，HTTP 健康接口为 ok/redis，产物与会话目录就绪。数据盘检查时使用率 70%、约 3.2 T 可用。未重启服务或停止用户会话；这些结果不替代完整功能复测与长期监控。
