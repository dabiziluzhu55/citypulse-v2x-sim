## 正确性修复

1. **3D 切换回滚**：保存已提交镜头状态；当前切换失败时，统一恢复车辆过渡、路口选择和镜头。旧事务不能回滚新事务。增加明确的失败日志。
2. **Redis 顺序保护**：拒绝旧序号及重复数据，兼容原协议复用序号的终态转换。Worker 新发布的终态使用递增序号，避免去重吞掉 COMPLETED/STOPPED。
3. **指标入口保护**：在更新区域成员、等待量、制动量之前过滤倒序和重复时刻，保留原有诊断提示。
4. **可靠评价采样**：Worker 在发送快照前将压缩记录写入每个会话的 evaluation.sqlite。指标订阅按序补读，后端重启可重放；页面继续使用实时推送。这里保存的是每个发布快照，不是每个 0.1 秒 SUMO 内部步。
5. **减少记录开销**：同一快照的 JSON 在磁盘记录与 Redis 发送之间复用，避免重复序列化。SQLite 连接明确关闭。
6. **WebSocket 首次读取**：同步订阅读取移出事件循环。
7. **容器更新后的 API 502**：Nginx 使用 Docker DNS 动态解析 backend，避免长期缓存已被替换的容器地址。

进一步加载原开发目录的原统计类，对同一份完整输入重放：三个场景的全部指标载荷与修复版统计类相等。这证明同输入下公式没有变化；并不意味着原版原有丢帧采样的历史数值都应被保留。

独立重放没有额外装载车辆燃油密度元数据，因此在线指标核对聚焦上述四项；原/新统计类的全部载荷比较采用相同元数据条件，不能据此声称燃油指标绝对精度已额外验收。

## 交通流生成专项

优化函数：`simulation/sumo/building/build_traffic.py::_route_contains`。
原实现对路线每个位置建立切片、重复比较；新实现先用序列原生索引查找目标首边，只在候选位置比较完整路径，仍支持重复边与空路径。

先在真实 20 路口数据上运行候选生成分析。带 cProfile 的阶段约 473 秒，其中匹配生成器约 19.44 亿次调用，外部 duarouter 调用约 130 秒。cProfile 数字用于定位，不能直接当作优化前的正常运行时间。

随后复用相同四类车辆 duarouter 原始输出，比较完整候选读取、匹配和筛选，避免重新路由影响结果：

| 候选处理 | 墙钟耗时 |
|---|---:|
| 原版匹配实现 | 153.62 秒 |
| 优化后 | 35.60 秒 |

本轮单次对照约加速 4.32 倍，耗时减少 76.8%。完整候选结果的 SHA-256 均为 `cc68594ab0199b67f2e546b9ceb12fb89b753c7ef5e17dea3ff2c130aaaba6c2`。

这是候选处理阶段的收益，不是整个交通流生成流程、SUMO 仿真或 GPU 推理的收益。未改变随机种子、交通需求、质量门槛，也没有跳过正式验证步骤。五千组随机路线/路径的等价测试覆盖空值、重复边、缺失边及 tuple/list 输入。

- 三场景对照脚本的总耗时包括独立重放，不能直接与此前单纯仿真完成耗时相除作为性能结论。
