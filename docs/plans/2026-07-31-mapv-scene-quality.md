# MapV Three 场景质量与连续性实施方案

## 目标与可行性

目标是让 20 个路口都具备稳定的建筑上下文、真实绿地/水系、连续道路和可读的路灯，并将整体层次向 MapV Three 亦庄示例靠拢。

可行，但需要区分两种观察尺度：

- 单路口视图可同时看到路口与 650 米范围内的大部分建筑。本地路口 tileset 继续按需切换。
- 20 个路口横跨约 30 千米，不能在浏览器中同时加载全部 208 MB、约 507 万顶点的本地建筑。全局视图使用百度建筑和路口标记，局部视图再叠加高精 tileset。

## 已确认原因

1. 本地建筑并未关闭。`VITE_ENABLE_XIONGAN_3DTILES=true`，20 个环境清单均指向对应的 `/3dtiles/intersections/demo_N/tileset.json`。
2. 建筑稀疏来自源数据。各路口切片均存在，但三角面数量从 432 到 22,050 不等；低密路口无法通过提高 LOD 凭空补齐。
3. 绿地错误来自生成器。旧实现给每个路口写入一个半径 500 米、96 段的圆形 `green-ground`，并以正 Z 偏移渲染，因而覆盖底图要素。
4. 水系只配置了 `demo_2`。其他路口没有独立水系资产。
5. 路灯 GLB 本身约 9,705 顶点并带 PBR 纹理，主要问题是场景光照偏暗、材质色彩空间和灯罩没有发光层，而不是模型完全缺失。
6. 路口机位距离仅 110 米，导致建筑被近裁切和画面上下文不足。

## 实施结构

渲染顺序采用亦庄示例的分层原则：

1. 百度全域底图：真实绿地、水系、连续道路和稀疏建筑兜底。
2. OSM 水系与绿地面：只绘制真实闭合多边形，放在道路下方。
3. 百度道路与 SUMO 道路：保留全域连续路网，高精路口边界保留至少 22 米过渡。
4. 百度建筑与按路口本地 3D Tiles：百度补密度，本地瓦片提供近景纹理。
5. 高精路口、路灯、信号灯、车辆和路口标记。

## 数据与稳定性

- `npm run generate:intersection-environments`：从本地 `TotalMap.osm` 为 20 个路口生成真实 `green.geojson`、`water.geojson` 和设施清单。
- `npm run audit:intersections`：逐路口检查 tileset、子瓦片、三角面、绿地、水系、路灯和道路边界重叠，并写入 `outputs/intersection-environment-audit.json`。
- 建筑源覆盖不足被记录为 warning，不误报为“未加载”；缺文件、圆形绿底或道路边界断开会作为 error 阻止验收。

## 验收标准

- 20 个路口的建筑 tileset URL、瓦片文件和设施文件全部可访问。
- 不再存在 `green-ground` 圆形面，绿地/水系不会覆盖道路或建筑。
- 百度道路默认开启；每个路口至少两条道路到达局部场景边界，过渡重叠不少于 4 米。
- 路灯模型材质可辨识，灯罩具有发光层，实例化渲染不增加逐灯 draw call。
- 路口默认机位约 620 米，允许 100-1,200 米缩放；全局最大视距放宽至 3,200 米。
- 构建、道路、建筑、场景、设施、绿地和逐路口审计测试全部通过；浏览器逐一切换 20 个路口无加载错误。
