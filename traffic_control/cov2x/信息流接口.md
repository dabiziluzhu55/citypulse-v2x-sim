# CoV2X 车路云协同算法 · 部署与信息流接口

- 版本：v3（2026-08-31）
- 稳定入口：`traffic_control.cov2x`
- 默认候选：`cov2x_g30_temp_cap_u24`
- 部署边界：只需部署 `traffic_control/` 与 Python 运行依赖
- 性能状态：`NOT_RUN`，不得宣称 update #24 已优于 StrongMP

## 1. 自包含部署结构

`traffic_control.cov2x` 不再依赖 `algorithms/`。部署代码分为：

- `dispatch.py`：候选选择、生命周期和 `COV2X_*` 环境隔离；
- `candidates/`：候选 adapter，只负责校验和生命周期适配；
- `runtime/`：冻结 update #24 推理闭包；
- `communication/`：V2X schema、transport、event batch、sink 和 drain；
- `models/`：checkpoint 与 provenance manifest。

训练与历史实验仍保留在 `algorithms/`，但不进入部署依赖图。区域外 Fixed
逻辑仍由场景传入的受控路口集合决定，没有复制第二套场景路由。

## 2. 冻结候选

默认候选由以下组件组成：

- Road：frozen G30 actor；
- Cloud：frozen G30 actor；
- Vehicle：update #24 actor；
- Vehicle action：`temporary_base_relative_speed_cap_v1`；
- Vehicle 决策周期：5 s；
- movement resolver：`MovementApproachCorridorV1`；
- leader：sticky intersection × movement leader；
- SUMO 纵向安全与生命周期 release 语义保持不变。

每次 Vehicle 决策都从当前 `v_base_t` 重新计算：

```text
delta_v_max_t = current_v_base_t * 0.10
requested_delta_v_t = u_t * delta_v_max_t
v_adv_t = clip(current_v_base_t + requested_delta_v_t, 0, current_v_base_t)
```

不得从上一周期 `v_adv` 累积。负动作产生临时 cap，零或正动作恢复当前
native/base speed。

## 4. Protocol 2.0 控制面

模块公开：

| 函数 | 输入 | 输出 |
|---|---|---|
| `initialize(payload)` | 场景元数据 | ready、candidate、generation、V2X export capability |
| `step(payload)` | 当前全量观测 | signals、vehicles、diagnostics、`v2x` |
| `finish(payload)` | 收官观测 | 结算并清理候选状态 |
| `drain_v2x_events()` | 无 | 自上次 drain 后的事件批次 |
| `set_v2x_event_sink(sink)` | callable 或含 `emit()` 的对象 | 配置可选进程内消费者 |

`actions` 仍严格只包含 `signals` 和 `vehicles`。新增通信数据位于 step
返回对象的顶层 `v2x`，不会改变 SUMO action contract。

## 5. 后端 JSON 事件接口

每次 `step` 都返回当前 snapshot 的事件批次：

```json
{
  "schema": "cov2x.v2x.event_batch",
  "schema_version": "1.0",
  "episode_id": "episode-001",
  "snapshot_id": "episode-001:12",
  "event_count": 18,
  "last_sequence": 216,
  "sink_error_count": 0,
  "events": []
}
```

JSON Schema 文件：

```text
traffic_control/cov2x/communication/v2x_event_batch_v1.schema.json
```

每条事件稳定包含：

- `SEND / DELIVER / CONSUME / TTL_EXPIRED`；
- message type、message ID、snapshot、sequence；
- source/destination role 与 ID；
- logical phase、event/sent time、message age、TTL、expiry；
- causal parent IDs；
- payload 字段名；
- TTL drop reason。

为了避免 20 路口场景把展示流量放大成控制瓶颈，公开事件不重复传输原始
VehicleState/MAP payload，只暴露字段清单。后端展示消息拓扑、数量、生命周期、
延迟、TTL 和因果关系已经足够；控制动作仍从 `actions` 获取。

## 6. 三种消费方式

### 6.1 HTTP/Protocol 转发

后端直接读取每个 `step` 返回对象的 `v2x` 字段。这是跨进程接入的默认方式。

### 6.2 进程内 drain

```python
import traffic_control.cov2x as cov2x

batch = cov2x.drain_v2x_events()
```

drain 使用独立游标；重复调用只返回新事件，不影响 step 内联批次。

### 6.3 可选 stream sink

```python
from traffic_control.cov2x.communication import V2XEventDrain
import traffic_control.cov2x as cov2x

sink = V2XEventDrain(max_events=10_000)
cov2x.set_v2x_event_sink(sink)
cov2x.initialize(metadata)
events = sink.drain()
```

sink 是监控边界：消费者异常会累计在 `sink_error_count`，不会改变控制动作。
`V2XEventDrain` 有界并记录被覆盖事件数，避免后端消费变慢导致算法内存无限增长。
